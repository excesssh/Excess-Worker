# Linux CUDA status

The published Worker 0.2.0, sequence 26, has a confirmed Linux CUDA installation defect: the pinned runtime tar archives contain root-level regular files, while the installer expects one enclosing directory. Installing a CUDA model therefore refuses the archive. This does not affect the recorded CPU configurations.

The source correction accepts flat regular-file layout only for the exact pinned Linux CUDA runtime archives. Traversal, nested entries, links, duplicate names, special files and archive-size limits remain enforced. A private candidate completed actual model installation, pinned runtime verification and specialised model inspection; the correction is included in published 0.2.1.

The same test also identified a memory-monitor defect: the non-dumpable runtime is hidden by the controller's private procfs. Source now samples the read-only kernel cgroup memory counter, including service processes and charged cache. This conservative aggregate is distinct from process RSS; unavailable RSS is reported as zero. The existing hard cgroup ceiling and sampled whole-device GPU budget remain in force.

Initial confined CUDA startup failed. Device detection outside confinement succeeded, but that worker observed no GPU residency or complete layer offload and refused execution. Subsequent diagnostics identified additional driver initialization requirements. The current source and published 0.2.1 use `linux-cuda-device-budget-v2`: four exact read-only discovery files, the exact NVIDIA NUMA-information ioctl encoding, UVM range-group operations 23/24 and only local Unix sequence-packet sockets. The existing Landlock abstract-socket/signal scope and controller network namespace remain required; CPU socket rules stay unchanged. NUMA mutations, encoded variants of the added UVM operations, Unix streams/datagrams and socketpair remain denied.

The GPU helper embeds a small compatibility module that discards optional own-thread naming writes for exact task `comm` paths with mode `w` or `wb`. The helper materializes only these authenticated bytes in a sealed memory file and selects its fixed descriptor for loading; it adds no proc write grant or installed host-library sidecar. The helper hash and immutable seals protect the module. Anonymous memory files do not receive a Landlock path rule. Direct thread/process-memory writes remain denied. The existing supervision protocol and authenticated legacy v1 installation remain compatible.

Focused Linux kernel tests cover deterministic helper builds, loading the sealed module after confinement, immutable bytes, narrow open interception, exact ioctl encodings, CPU socket refusal and outside abstract-peer rejection. These checks contain no NVIDIA device or buyer execution. Current-source GPU hardware and buyer lifecycle verification remain open.

Source verification at `58f6a3e9dc4e87afbaf05ebc8ea2c2a3771e10d5` passes [the standalone workflow](https://github.com/excesssh/Excess-Worker/actions/runs/38100431756): Ubuntu had 307 tests, 300 passed and 7 skipped; Windows had 307 tests, 284 passed and 23 skipped. Both had zero failures or cancellations. Ubuntu also passed all six native controller/package fixtures. These results verify software and recorded kernel checks, without NVIDIA hardware or buyer execution.

Version 0.2.2 keeps the v2 helper and fixes streamed-text metering when the pinned runtime withholds token IDs inside a multibyte character (seen with gpt-oss). Its signed candidate, sequence 29, with the same payload as published sequence 30, ran actual Linux NVIDIA CUDA buyer jobs for all 17 pinned local models on one recorded NVIDIA B300 configuration (driver 580.178.04, CUDA 12.9, Ubuntu kernel 7.0.0-38-generic). Drain, restart, revocation and cleanup passed. GPU cancellation has runtime-monitor evidence for transcription only; text and image cancellations ended with no charge but without monitor evidence. See the [B300 record](linux-b300-cuda-sequence29.md).

Versions 0.2.0 and 0.2.1 make no Linux GPU claim, and their published assets remain unchanged. Other NVIDIA GPUs, drivers, kernels and distributions, multi-GPU hosts and hard VRAM isolation remain unverified. Do not treat catalogue availability, completed downloads, device detection or a software test as Linux GPU execution evidence.
